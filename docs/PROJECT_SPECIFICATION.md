# Спецификация проекта Family App

Версия документа: 1.0

Статус: спецификация первой версии приложения

## 1. Описание проекта

Family App — адаптивное семейное веб-приложение с общей учётной записью и отдельными профилями членов семьи.

Первый модуль приложения обеспечивает хранение, просмотр, редактирование, импорт и поиск медицинской информации:

- общих медицинских сведений;
- эпизодов заболеваний;
- медицинской хронологии;
- измерений;
- лабораторных исследований;
- посещений врачей;
- диагнозов и назначений;
- заметок;
- изображений и PDF-документов.

Интерфейс приложения предоставляется на русском языке и адаптируется для настольных и мобильных экранов.

## 2. Термины

### Учётная запись

Данные для входа в приложение. В первой версии одна учётная запись используется для управления семейными данными.

### Семья

Контейнер верхнего уровня, объединяющий профили людей и принадлежащие им данные.

### Член семьи

Профиль человека внутри семьи.

### Медицинский профиль

Набор актуальных медицинских сведений человека.

### Медицинское событие

Запись медицинской хронологии с датой, типом, описанием и связями с предметными данными.

### Эпизод

Ограниченная по времени совокупность медицинских событий, относящихся к одному состоянию или заболеванию.

### Тип показателя

Описание измеряемой характеристики, её формата и единицы измерения.

### Измерение

Значение показателя, зафиксированное для человека в определённый момент времени.

### Лабораторное исследование

Набор результатов анализа, связанных общей датой, названием и лабораторией.

### Вложение

Изображение или PDF-документ, связанный с медицинской записью.

## 3. Пользователь и доступ

Система должна предоставлять:

- вход по email и паролю;
- выход из учётной записи;
- восстановление пароля;
- восстановление активной сессии после перезагрузки страницы;
- завершение недействительной или истёкшей сессии;
- доступ только к семье, связанной с текущей учётной записью;
- создание семьи при первоначальной настройке;
- хранение идентификатора семьи во всех семейных сущностях.

## 5. Семья и профили людей

### 5.1. Семья

Семья содержит:

- уникальный идентификатор;
- отображаемое название;
- дату создания;
- дату последнего изменения.

### 5.2. Член семьи

Профиль человека содержит:

- уникальный идентификатор;
- идентификатор семьи;
- фамилию;
- имя;
- отчество;
- дату рождения;
- пол;
- семейную роль;
- статус профиля;
- дату создания;
- дату последнего изменения.

Поддерживаемые значения пола:

- мужской;
- женский;
- не указан.

Семейная роль задаётся текстовым значением. Примеры: родитель, ребёнок.

Статусы профиля:

- активный;
- архивный.

Система должна предоставлять:

- список членов семьи;
- создание профиля;
- просмотр профиля;
- редактирование профиля;
- перевод профиля в архив;
- восстановление профиля из архива;
- выбор текущего члена семьи при добавлении медицинских данных.

## 6. Медицинский профиль

Медицинский профиль связан с одним членом семьи и содержит:

- группу крови;
- резус-фактор;
- аллергии;
- хронические состояния;
- медицинские предупреждения;
- общий комментарий;
- дату создания;
- дату последнего изменения.

Группа крови принимает значения:

- I (O);
- II (A);
- III (B);
- IV (AB);
- не указана.

Резус-фактор принимает значения:

- положительный;
- отрицательный;
- не указан.

Аллергии, хронические состояния и предупреждения представлены отдельными элементами. Каждый элемент содержит:

- уникальный идентификатор;
- название;
- описание;
- статус актуальности;
- дату добавления;
- дату последнего изменения.

## 7. Главная страница

Главная страница должна отображать:

- список активных членов семьи;
- активные медицинские эпизоды;
- последние медицинские события;
- действия быстрого добавления;
- переход к глобальному поиску.

Для каждого члена семьи отображаются:

- ФИО;
- возраст;
- семейная роль;
- количество активных эпизодов;
- дата последнего медицинского события.

Действия быстрого добавления:

- создать эпизод;
- добавить измерение;
- добавить лабораторное исследование;
- добавить посещение врача;
- добавить документ;
- добавить заметку;
- импортировать JSON.

## 8. Медицинская хронология

Медицинская хронология отображает события человека в обратном хронологическом порядке.

Медицинское событие содержит:

- уникальный идентификатор;
- идентификатор семьи;
- идентификатор человека;
- идентификатор эпизода при наличии;
- тип события;
- дату и время события;
- заголовок;
- текстовое описание;
- источник данных;
- автора записи;
- дату создания;
- дату последнего изменения.

Типы событий:

- заметка;
- измерение;
- лабораторное исследование;
- посещение врача;
- назначение;
- документ;
- начало эпизода;
- завершение эпизода.

Источники данных:

- ручной ввод;
- JSON-импорт.

Хронология должна предоставлять:

- постраничную или бесконечную загрузку;
- фильтр по периоду;
- фильтр по типу события;
- фильтр по эпизоду;
- просмотр подробностей события;
- переход к связанной предметной записи;
- редактирование поддерживаемых записей;
- удаление записи с подтверждением.

- заметки;
- названия, подписи и описания документов.

### 17.2. Фильтры

Поиск предоставляет фильтры:

- член семьи;
- начальная дата;
- конечная дата;
- тип записи;
- эпизод;
- статус эпизода;
- тег.

### 17.3. Результаты

Каждый результат поиска отображает:

- тип записи;
- заголовок;
- фрагмент найденного текста;
- ФИО человека;
- дату события;
- связанный эпизод;
- переход к подробной странице.

Поиск должен поддерживать русскоязычный текст и регистронезависимое совпадение.

## 19. Требования к интерфейсу

Интерфейс должен:

- работать на экранах шириной от 320 пикселей;
- поддерживать управление мышью, клавиатурой и сенсорным экраном;
- использовать единый формат дат и времени;
- отображать даты в локальном часовом поясе пользователя;
- сохранять даты событий в формате ISO 8601;
- предоставлять понятные состояния загрузки;
- предоставлять пустые состояния списков;
- отображать ошибки рядом с соответствующими полями;
- предупреждать о несохранённых изменениях;
- запрашивать подтверждение удаления;
- использовать доступные подписи элементов управления;
- поддерживать видимый фокус клавиатуры;
- сохранять читаемость при увеличении масштаба интерфейса;
- предоставлять текстовые обозначения состояний вместе с цветом.

На мобильных экранах основная навигация и действие добавления должны оставаться доступны без горизонтальной прокрутки страницы.

## 23. Безопасность данных

Система должна обеспечивать:

- хранение паролей средствами провайдера авторизации;
- защищённые cookie сессии;
- проверку аутентификации на сервере;
- проверку принадлежности каждого объекта семье;
- Row Level Security для таблиц Supabase;
- закрытый bucket для медицинских файлов;
- временные подписанные ссылки;
- отсутствие серверного ключа Supabase в клиентском коде;
- валидацию MIME-типа и размера загружаемых файлов;
- экранирование отображаемого пользовательского текста;
- защиту изменяющих запросов;
- ограничение частоты запросов авторизации и импорта;
- исключение медицинских данных и исходного JSON из технических логов;
- удаление временных файлов после обработки;
- безопасное хранение секретов в переменных окружения.

## 24. Проверка данных

Входные данные API и JSON-импорта проверяются схемами Zod.

Проверка должна охватывать:

- обязательные поля;
- UUID;
- даты и время;
- допустимые значения перечислений;
- числовые диапазоны;
- соответствие значения типу показателя;
- единицы измерения;
- длину текстовых полей;
- количество элементов в массивах;
- тип и размер вложений;
- принадлежность связанных сущностей одной семье и одному человеку.

Некорректные данные не должны частично сохраняться.

## 25. Поиск и индексация

Поисковый слой реализуется через `SearchRepository`.

PostgreSQL-адаптер должен:

- формировать поисковое представление медицинских записей;
- обновлять индекс при создании, изменении и удалении данных;
- использовать полнотекстовый поиск PostgreSQL;
- поддерживать русскоязычные запросы;
- применять семейный фильтр до возврата результатов;
- поддерживать пагинацию и сортировку по релевантности и дате.
